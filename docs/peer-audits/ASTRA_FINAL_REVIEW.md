**R1 — Bind every effect-bearing primitive to the authorized action.** Evidence: `participant/agent.py:440-461`, especially the `isinstance(value, str)` condition at line 451; `participant/authorization.py:72-145`. Schema validation checks a numeric argument's type, while the authorization checker verifies the imperative and target words. Neither checks an ordinary numeric quantity against the user's command. An offline controller probe supplied the real text `Hold 2 units of ITEM-82 for Nia.` and a schema-valid proposal with `quantity: 2000`, the same item/customer, and the exact current quote. The controller emitted `hold_inventory(..., quantity=2000)`. Running the same probe against the checkpoint class reproduced it there too. This is a demonstrated boundary failure under an erroneous planner proposal, not a claim that a live model has already made this mistake.

Minimal fix: require source evidence for effect-bearing numbers and booleans as well as identifiers/strings. Use an exact typed user value, a verified result binding, or explicit confirmation of the concrete argument set. If a generic natural-language value cannot be bound unambiguously, clarify; do not add a growing number-word/domain parser or merely test whether the number occurs somewhere in the message. Declared defaults/enums need a deliberate authorization policy rather than becoming permission to substitute a conflicting supplied value. Test: mutate quantity `2 -> 2000`, a nested amount, and a boolean flag under an unchanged quote and require zero writes; the exact authorized values and validated result-bound values must still work. Retain the existing reported/negated/conditional-command tests.

**R2 — Expiry must retire continuation authority just like an ambiguous error.** Evidence: `participant/agent.py:270-276`, `589-615`, `630`. `_result` sets `result_announced` after an ambiguous write error, and `_continue_result` respects it. `_expire_writes` marks the operation unknown and emits a final response but never retires that continuation. Reproduction: authorize `Create a note saying hello. Then create another note saying extra.`, dispatch the first note, move its deadline into the past, call `_expire_writes`, then deliver its late success. Output is first `tool_call`, final unknown-outcome notice, then a new `tool_call` for the second note. The checkpoint does the same. The branch's new regression at `tests/test_participant_controller.py:550` covers the error-notification path, not local expiry.

Minimal fix: mark the continuation retired when the controller declares that operation's outcome unresolved at its deadline, before emitting the notice. Reuse the existing guard if its semantics remain clear. Late success must still update the durable ledger and receipt, without silently restarting the settled chain. Test: exercise both explicit ambiguous error and absence-of-result expiry, release the same late success, and assert one submitted effect, a reconciled receipt, and no continuation or obsolete final speech. Also cover expiry shortened by `scenario_end`.

**R3 — Unknown-write protection must survive wordless barge-in followed by speech.** Evidence: `participant/agent.py:206-215`, `517-525`. The new cross-revision check runs only when `messages[_request_start].event_type == 'interruption'`. A wordless interruption followed by a completed speech/audio request advances `_request_start` again to the speech/audio message, so it bypasses the check. Reproduction: submit `Send a message to Nia saying hello.`, return `error: timeout`, send a wordless interruption, then repeat the same request as `user_speech_chunk`. The ledger contains an `unknown` first write and a `pending` second write with identical arguments. Putting those same words directly on the interruption is blocked by the new guard. The effect safety policy should not depend on these equivalent transport encodings.

Minimal fix: check unresolved equivalent writes independently of the most recent event type. Reconcile the first outcome, or obtain an explicit instruction to create an additional effect despite that uncertainty. This is distinct from a genuinely new repeated action after a confirmed outcome, which can remain allowed. Test the direct interruption, wordless-interruption-plus-text, wordless-interruption-plus-audio, and split speech encodings against both `unknown` and `cancel_requested`; none should duplicate an unresolved effect. Preserve a positive test for an independently authorized additional operation.

**R4 — An unavailable image must not make a printed-text proposal easier to accept.** Evidence: `participant/media.py:243-249`; `participant/planner.py:1131-1135`, `1620-1648`, `1667-1688`; `tests/test_participant_visual_recognition.py:192-231`. The loader now catches image failure, marks `image_unavailable`, and returns no image source. `_validate` consequently has `has_image == False` and skips the entire `result_evidence.target_basis == 'printed_text'` gate. Using the real loader/planner with `httpx.MockTransport`, a nonexistent `missing.png`, and `What is the port in this picture?`, I returned zero observations plus a `manual(query='LAN')` proposal claiming printed-text evidence. The controller dispatched the read. The existing missing-frame test scripts a compliant clarification from the fake model; it does not test rejection of this ungrounded proposal.

Minimal fix: validate visual evidence based on what the proposal claims, even when no media was attached. `printed_text` always requires a clear current-frame label from a successfully prepared source. Clear or retire stale image observations when that source is unavailable. Keep the desired recovery in which an unrelated later text question can proceed; do not make one bad frame poison every later turn. Test: missing/corrupt image plus a fabricated printed-label proposal must dispatch nothing; a later explicit non-visual lookup or arithmetic answer must still work. Include unavailable replacement frames and stale prior observations.

**R5 — Matching arguments do not establish freshness or current provenance.** Evidence: `participant/agent.py:464-486`, `524-537`. Every successful old read with matching arguments/slots becomes eligible for reuse across revisions, with no immutable-result declaration, freshness limit, current user selection of that old result, or manifest identity check. Reproduction: `temperature(room='lab')` returns `19`; on a later `Read the current temperature in lab again now.`, the controller emits `Temperature 19.` without a new tool call. It also appends a copied result with revision 2 although the durable `call-1` operation is from revision 1. An interrupted read that completes late can subsequently enter the same reuse path. Price, availability, weather, inventory, and other mutable reads are affected even if their arguments remain identical.

Minimal fix: remove general cross-turn reuse for the release candidate. If retaining the explicit "sort the previous result" behavior, make it operate on an explicitly referenced prior result while preserving its original call/revision and source identity, rather than pretending a fresh read occurred. Do not add a generic cache framework. New requests for live data and changed manifests must dispatch anew. Test: mutable data changes between identical queries and the second answer must use a second call; a late superseded result must not become a fresh answer; explicit readout/sort of a prior immutable result may reuse it with honest provenance. Verify that result-bound continuations consult the same ledger identity rather than a synthetic revision copy.

**R6 — Remove the fixed 10 ms fence; it is not a causal ordering guarantee.** Evidence: `participant/agent.py:88-95`; `tests/test_participant_controller.py:1001-1021`; official `harness/runner.py:103-110` and `harness/scorer.py:301-309`. The unfenced unseen-tool trace logs both delivery of the final user chunk and the acknowledgment at 796 ms, while the scenario's nominal timestamp is 800 ms. The scorer ignores that causally subsequent acknowledgment because it compares against the nominal schedule. This is not evidence that THREAD acted before receiving the final chunk. The new sleep delays handling, invalidation, acknowledgment, and planning for every completed speech/audio chunk; it does not know the evaluator clock epoch, time scale, or maximum lead. Its unit test proves only that `sleep(0.01)` was invoked.

The later focused fenced unseen-tool sample has acknowledgments at 812–813 ms and full latency credit. That is evidence of favorable timing in those three attempts, not a universal fence guarantee or an isolated benefit estimate. The complete fenced package scored 78.0 versus 90.6; hosted responses and run conditions changed, so attributing the 12.6-point decline to ten milliseconds would also be unjustified. The ten milliseconds cannot explain the observed multi-second provider failures by itself.

Minimal fix: remove the production sleep and preserve immediate receipt-based turn processing. Keep official harness/scorer bytes unchanged and report the nominal-versus-observed timestamp discrepancy alongside the official score. A true future clock fix requires an agreed epoch/receipt contract, not a larger guessed sleep. Test causal behavior: no acknowledgment/dispatch before turn closure; queued corrections win; scheduling jitter does not cause duplicate speech or effects. Use controlled events/clock injection, not an assertion that one particular delay constant exists. Any decision to retain a timing shim needs an explicit measured scope and paired frozen evaluations, not a claim of general correctness.

**R7 — The acoustic test can time out before its mocked request ever starts.** Evidence: `tests/test_participant_audio_staging.py:520-547`, especially the 40 ms budget at 531 and two-second arrival wait at 536; `participant/planner.py:1466-1481`. I reran this exact test with only an injected 80 ms `MediaLoader.prepare` delay. It deterministically errored at line 536 after 2.073 seconds. The ordinary full suite passed; this adversarial result explains why the change is not a complete flake fix.

Minimal fix: isolate the intended same-turn-job/deadline property with controlled preparation and a controllable clock/timer boundary. Keep the separate existing test at line 475 proving that preparation consumes the budget and must prevent a late acoustic dispatch. Test under delayed preparation as well as a deliberately stalled acoustic response; both should assert their intended branch rather than assume host startup fits inside 40 ms. Do not inflate the production deadline or repeatedly rerun until green.

**What held up under inspection and verification.** The controller remains the sole effect emitter. Ready plans carry a revision; queued corrections precede result-to-write continuations; old outcomes remain in the ledger while stale speech/continuations are suppressed. Duplicate terminal results cannot replace first terminal evidence. Result bindings resolve actual call IDs and typed paths, reject mismatched values, and demand a current explicit reference for an old source. These are useful protections, but R1–R5 delimit their guarantee.

Audio preparation validates and hashes the exact bytes attached to the native request. The independent acoustic pass runs alongside MAIN, compares current observations, and vetoes uncertainty or disagreement. `_audio_key` includes message index, message revision, MIME, and SHA-256; jobs are retired before cancellation and clear cache promotion occurs only after the outer accepted plan. The single-call mode has additional retained-source checks. Image embeddings are real provider vectors validated for dimensions/finiteness and matching input SHA-256; they are attached only if already ready, and planning does not wait for them. Neither a matching hash nor a model's `selected_label` attestation proves recognition accuracy. R4 is an actual missing-source acceptance hole; routine in-range metadata checks cannot compensate for it.

The audio repair added at `participant/planner.py:666-682` is bounded to one terminal `flight_search` with matching independent readings and an earlier explicitly superseded destination. It cannot directly authorize a write. It is nevertheless a documented flight-specific heuristic, not evidence of domain-general correction understanding. I found no public scenario-ID or expected city/image lookup table in the production changes. Future improvements should use varied tool descriptors and source evidence rather than extending these flight grammar exceptions to chase one public clip.

The proposed mailbox in `docs/peer-audits/visual-read-deadline.md:13-19` is **NO-GO as written**, even for reads. Its tests demand both dispatch before the final response field arrives and no dispatch for malformed/truncated streams. The smallest useful first experiment is a **short, complete decision envelope** containing current-source observations, one validated terminal read, and its result contract, with optional explanatory prose deferred to the existing result renderer. Accept only after the whole envelope is complete, well-formed, duplicate-free, and valid. This can shorten the full-response barrier without introducing a partial-object effect path. If later using streaming, define an explicit immutable commit envelope so subsequent data cannot change its calls, uncertainty, or clarification; validate its completion atomically. Register once in the existing ledger, bind revision/frame digest/current manifest, and recheck queued input immediately before dispatch. Do not clone the controller into the planner or allow an early read to carry a write continuation. Optional embedding remains opportunistic and may miss its bonus when dispatch moves earlier.

Acceptance tests must cover identical valid prefixes with truncated/contradictory endings, duplicate keys, Unicode/chunk splits, false/missing current-label evidence, changed bytes under the same frame reference, replacement frame, manifest kind changes, expired deadline, correction queued at commit, repeated mailbox delivery, and late results. Malformed pre-commit data must emit no call; at most one operation may follow a valid immutable commit. Measure first complete admissible-envelope time, final decision time, tool completion, final response, and embedding attachment separately before claiming a latency gain. The saved traces establish a reason to measure this experiment, not its expected improvement.

**Generic route most likely to help without public-case fitting.** The supported direction is a bounded decision pipeline shared across modalities, preserving the deterministic ledger/source/authorization checks. This is a proposed experiment, not a proven performance claim:

1. Preserve immediate acknowledgment of a completed turn and canonical ordered input. Keep provisional chunks non-authoritative; attach source identity and explicit correction relationships to the completed turn. Do not match scenario IDs, recorded filenames, city names, or one port label.
2. Produce the smallest complete action decision from the current runtime manifest. Carry source-bound argument evidence and an honest result contract; defer optional narration until a result exists. Rename tools and reshape nested results in tests. Share one absolute turn budget across retries/replans; reserve expected tool/result time using the actual remaining deadline and manifest delay bounds. `agent.py:258` already supplies `tail_remaining_ms`, but `_decide` does not use it to schedule a completion budget.
3. For audio, keep independent verification as default. Generalize only meaning-preserving formatting comparison with adversarial controls for negation, numbers, names, and corrections; do not broadly weaken disagreement vetoes. Local transcript-first reads are a separate opt-in trial only after a validated `clear/uncertain/unknown` output exists. A fluent wrong transcript with a valid digest is still wrong. The current local ASR reduced acoustic time without removing MAIN timeouts, so merely replacing ASR is insufficient. Serial ASR plus text planning can also exceed the same deadline; measure the whole route.
4. For route availability, a validated alternate provider with an in-process health/circuit decision and one shared deadline is worth testing separately. Start with a known unhealthy/429/503 route being skipped before the next turn; any same-turn recovery gets only the original remaining budget. Each candidate must pass the same source, uncertainty, schema, and action gates. No automatic promotion, long retry waterfall, or fallback after effects. Transport recovery cannot fix a plausible but incorrect HTTP 200 interpretation. Existing Groq/quota and alternative-provider probes do not establish a ready substitute.
5. Freeze the changed artifact and repeat the untouched official 9 × 3 evaluation in multiple independent batches, while also using a separate varied corpus with new names, tools, schemas, speakers, accents, ambiguous audio, corrections, and replacement frames. Record false acceptance, unnecessary clarification, completion rate, per-case minima, and full-decision/final-response tail latency. Select on those measures rather than maximizing one median public score. Retain failed attempts and source/model/artifact identities.
