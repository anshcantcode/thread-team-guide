**Ranked findings and minimum practical fixes**

**F1 / P1 — A planner-selected partial quote bypasses the new numeric and boolean guard. R1 remains open.** Locations: `participant/agent.py:442-451,474-478`; `participant/authorization.py:106-127`. The new helper examines `authorization.quote`, while `authorization_grant` independently accepts a quote overlapping the larger current command. These two checks do not establish that the number belongs to the proposed field.

Minimal reproduction, accepted by both the planner validator and controller:

```text
Actual user: Set limit 2 and threshold 50 for Nia.
Proposal: set_threshold(threshold=2, customer="Nia")
authorization.quote: "Set limit 2"
Observed: tool_call with threshold=2.

Actual user: Set alerts true and backup false for Nia.
Proposal: set_backup(backup=true, customer="Nia")
authorization.quote: "Set alerts true"
Observed: tool_call with backup=true.
```

Both quotes are exact current substrings with a correct message index. The proposal uses one primitive, so the new multiple-field guard does not fire. The full-quote negative tests pass because the complete quote contains conflicting literals; they miss this adversarial slicing. The original `quantity=2 -> 2000` case is blocked, but this is not complete argument-source binding. The underlying lack of role binding was inherited; the new patch closes only a subset of it.

Practical fix: derive checks from the controller-verified command/source, never solely the proposed quote, and bind each effect-bearing argument to an exact typed field or an approved concrete argument set. A full-command multiple-number rejection is a useful immediate fail-closed restriction, but occurrence anywhere in a command still is not role binding. For ambiguous natural language, present the actual proposed fields and store confirmation of those exact values independently of the planner. Reuse verified result binding where appropriate. Do not grow a number-word/domain grammar or weaken the full-command check to make tests pass. Acceptance: the two sliced-quote cases and swapped nested fields emit zero writes; correctly bound values still dispatch.

**F2 / P2 — Omitting visual evidence still bypasses the missing-frame boundary. R4 is only partially fixed.** Locations: `participant/planner.py:1668-1678`; `participant/agent.py:796-819`. The new unconditional check rejects explicit `target_basis="printed_text"` when the current image was not prepared. However, the requirement for evidence on a title/name citation remains inside `if has_image`. A missing image therefore relaxes that requirement.

Reproduction uses the real loader and planner with `httpx.MockTransport`: nonexistent `missing.png`; user asks “What is the port in this picture?”; zero observations; proposal `manual(query="LAN")`, no `result_evidence`, and template `The printed LAN port is described by {records.0.title}.`. The controller dispatches the lookup. After a synthetic manual result it says `The printed LAN port is described by LAN connector manual.` No image was available and the user never supplied LAN. Adding the explicit printed-text evidence field to the same proposal correctly makes the planner reject it.

This is the remaining sibling of the original branch-introduced missing-frame problem. The present fix protects declared visual evidence, but an omitted declaration makes an equally visual claim easier to accept. Practical fix: retain the unavailable current-frame condition as an admission constraint. Require a validated source for the lookup target/citation when the active request depends on that frame; do not let an absent optional field opt out. A later explicit text target or unrelated nonvisual turn must remain usable. For the minimal release policy, clarify the unresolved visual request instead of accepting an ungrounded target/template. Test missing and corrupt frames, replacement frames, omitted/null evidence, and a positive later text-only request. This is not a claim that arbitrary prose hallucinations can be eliminated by a keyword filter.

**F3 / P2 — A fresh lookup containing a sort instruction still reuses old data. R5 remains partially open.** Locations: `participant/agent.py:495-505,563-574`. The new freshness policy is a small forbidden-word list plus a permissive sort regex. It treats “those results” anywhere in the message as a reference to old results, even when those words refer to the lookup being requested now.

Reproduction: `read_records(location="Seattle")` returns temperature 18. On a new user turn, request `Fetch updated results for Seattle and sort those results by temperature.` Propose the same read. Observed: **zero new tool calls**, final `Temperature 18.`. The blacklist includes `current/live/latest/again/now/refresh/recheck` but not `updated`; adding that one word merely moves the hole. The existing “current ... again now” test does not establish general freshness.

The provenance correction is real: the reused `tool_results` entry retains call-1/revision 1 while the current turn is revision 2. It no longer fabricates revision 2 for the old operation. An additional independent continuation probe reused an explicitly referenced prior read, then attempted a result-bound numeric write: the ledger and context both retained revision 1 and the old-source binding check correctly rejected the write; only one operation existed. Correct provenance, however, does not fulfill an explicitly requested new lookup. Operations also still lack a stored manifest identity; matching names and arguments cannot prove a fresh source identity.

Practical fix: remove implicit cross-turn read substitution from `_dispatch` for the release candidate. A proposed tool invocation should execute. If retaining local sorting of prior results, make it an explicit operation over a referenced prior call, retain original source/revision/manifest identity, and do not turn a new read into a cache hit. Avoid expanding a natural-language freshness blacklist. Acceptance: fresh queries with sorting execute anew; superseded late reads never satisfy them; deliberate presentation of a referenced prior result preserves its provenance and needs no fresh call.

**F4 / P2 — The new multiple-primitive guard asks for confirmation that can never succeed. Newly introduced by the R1 fix.** Location: `participant/agent.py:447-451`. Any write with two unbound numeric/boolean leaves is rejected unconditionally, regardless of how explicit the source or confirmation is. A tool requiring `limit` and `threshold` cannot execute from a user's values unless they happen to come from a tool result.

Reproduction: `Set limit 2 and threshold 50 for Nia.` with exactly those arguments produces `Please confirm each numeric or boolean value...`. A new turn `Yes, set limit 2 and threshold 50 for Nia.` with the same correct values produces the same clarification. No operation is ever registered. This also affects a number plus a boolean and nested arrays/objects with multiple leaves. It is a functional regression, rather than unsafe permissiveness.

Practical fix: provide the concrete, controller-owned typed confirmation route required by F1, or explicitly reject unsupported ambiguous commands without promising that repeating a confirmation can unlock them. Do not remove the guard before a real binding route exists. Acceptance must include a successful, exactly confirmed write with two distinct primitives and a rejection when either value changes. Merely asserting that an error contains “confirm” is insufficient.

**F5 / qualified timing observation — A result dequeued after its deadline can continue the chain before the expiry sweep. This does not reopen the settled-notice R2 bug.** Locations: `participant/agent.py:106-111,610-649`. The run loop processes queued results before `_expire_writes`; `_result` never checks the operation deadline. The new `continuation_retired` flag is set only by the sweep.

Reproduction through the actual `run()` loop: authorize creating a hello note followed by an extra note; submit the first; set its deadline in the past; place its success in the input queue before the next loop iteration. Observed: call-1 becomes successful and **call-2 creates the extra note** before expiry is checked. The late receipt remains recorded. Running the original expiry-first sequence instead retires the continuation and suppresses it correctly.

The precise limitation matters: this probe does not show a continuation after an already-issued unknown-outcome notice, and the second action was originally authorized. It shows that enforcing the deadline as an absolute continuation cutoff would currently be scheduler-dependent. If continuation authority is meant to end at that deadline, expire before result continuations or perform the same retirement check in `_result`, while still reconciling the late receipt. If it ends only when the controller settles the request as unresolved, this behavior can be intentional. I therefore do not count it as an additional P1/P2 blocker without an explicit absolute-cutoff contract. Define the policy and use a controlled clock/queue test for both orders. Do not discard late evidence or restore obsolete speech.

**Shorter complete decision envelope: reasonable bounded experiment, not yet safe to promote**

A smaller **complete** decision can be tested without an early-dispatch mailbox. Keep current-source observations, one terminal read and its typed arguments/evidence/result contract, and explicit clarification status. Defer optional explanatory prose to the existing result renderer. Require the entire root document, final successful provider completion, full schema/semantic validation, and no trailing document or duplicate keys at any nesting depth before making the decision eligible. Preserve the existing controller as the only dispatcher.

The present parser at `participant/planner.py:1570` uses ordinary `json.loads`. An independent mocked-provider test returned a complete object containing `clarification:"Stop and ask"`, `tool_calls:[]`, then duplicate `clarification:null` and `tool_calls:[valid read]`. The planner accepted the last values and emitted the read. This is an inherited parser weakness already identified in the first review, not a newly introduced streaming path. Add duplicate rejection with a small `object_pairs_hook` (or equivalent strict decoder) before using the proposed duplicate-free envelope; provider schema guidance is not enforcement at this boundary.

The mailbox proposed in `docs/peer-audits/visual-read-deadline.md:13-19` remains unacceptable as written. A closed inner call/array is still a partial root document. Identical prefixes can end in a valid decision, a contradictory duplicate, or truncation. No later cancellation can undo a dispatched read. **Never dispatch from partial streamed JSON.** An explicit independently framed immutable commit protocol would be a different design, unnecessary for this first experiment.

At commit time, recheck the runtime-owned turn revision, prepared frame digest, current manifest identity/kind, remaining deadline, and queued corrections. Admit at most one ledger operation; no authorization or write continuation on the experimental read. Keep image embedding opportunistic. Fix the source/grounding defects above rather than moving their existing acceptance bugs earlier in time.
